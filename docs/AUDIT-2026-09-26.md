## 2. Documentation consistency

`README.md`, `ARCHITECTURE.md`, `PROGRESS.md`, and `docs/SECURITY-STATUS.md` were read end to end. Every
"implemented" claim was checked against code rather than against the document's own wording.

The documents are unusually accurate about **what exists**. The broker is genuinely deny-by-default
with no grant path for `environment.inspect`; the path protection genuinely uses `NO_READ_UP` rather
than a DACL; the empty-environment block is genuinely built and genuinely correct; the five broker
categories are genuinely disjoint from the five policy-gate categories; the replay projection genuinely
excludes PID, exit code, and CPU time. Those checks all passed.

The failures are narrower and sharper: a small number of claims that are **broader than the code**,
and a systematic lag of one milestone.

### 2.1 Claims contradicted by the code

#### (a) Denied spawns do not record a `ProcessLifecycle` — CRITICAL

Both `ARCHITECTURE.md:124-127` and `docs/SECURITY-STATUS.md:51` claim that **every** requested spawn
records a `ProcessLifecycle` including "authorized **or denied**."

They do not. On the denial branch, `crates/engine/src/lib.rs:461` sets `process_lifecycle: None` and
`:460` sets `broker_denial: Some(denial)`. `ProcessLifecycle::authorized`
(`crates/engine/src/lib.rs:499-500`) is the only lifecycle constructor the engine ever calls.
`ProcessLifecycle::denied` exists at `crates/core/src/execution.rs:538-544` but is referenced only
from `#[cfg(test)]` code at `crates/core/src/execution.rs:717` and `:808` — it is dead in every real
path.

The repository's own test suite asserts the opposite of the documentation, in prose, at
`crates/engine/tests/process_spawn.rs:246-247`: *"never records a process lifecycle because nothing was
ever requested of the OS"*, with matching assertions at `:276-278` and `:304-307`. As a consequence
`crates/evaluator/src/lib.rs:220-233` is unreachable from the engine.

A document that is falsified by a passing test in the same repository is the worst class of
documentation defect, because a reader has no way to discover it.

#### (b) The containment layer is not yet load-bearing

`ARCHITECTURE.md:99-100` says `process.spawn` "is the permission that makes the containment layer a
real boundary rather than a library nothing calls." `README.md:86` and `PROGRESS.md:17` make the same
implication.

In the shipped product, the containment layer **is** a library nothing calls. The executable path is
unreachable with any shipped benchmark: `GridWorldBenchmark::capability_policy()` returns
`CapabilityPolicy::deny_all()` (`crates/benchmarks/src/lib.rs:189-191`), and the benchmark does not
override `process_spawn_plan()`, so the trait default `None` applies
(`crates/core/src/traits.rs:93-95`). `spawn_request_for` therefore yields `program: ""`
(`crates/engine/src/lib.rs:830-836`), which the broker always refuses
(`crates/broker/src/lib.rs:220-230`, `:275-278`). `ContainedProcessSpawner::spawn_contained` is reached
only by the synthetic `SpawnBenchmark` defined in `crates/engine/tests/process_spawn.rs:59-149`.

The repository already concedes the underlying fact in three other places
(`ARCHITECTURE.md:67`, `docs/SECURITY-STATUS.md:91`, `:109`) but not in the three places that carry the
headline claim.

#### (c) The configuration fingerprint hashes six fields, not five

`ARCHITECTURE.md:49` states the fingerprint hashes "only model name, temperature, max tokens, prompt
template version, and benchmark version." `FingerprintInput` has six fields
(`crates/model-adapters/src/lib.rs:388-407`); `timeout_seconds` is declared at `:393` and fed into the
hash at `:404`.

Low severity — a timeout is not secret — but the word "only" is load-bearing in a reproducibility
contract.

#### (d) `environment.inspect` contradiction inside one document

`docs/SECURITY-STATUS.md:101` says an authorized `environment.inspect` returns
`EngineError::CapabilityExecutionUnsupported`. That branch is unreachable for that permission:
`crates/broker/src/lib.rs:203-207` denies it as the first match arm of `review()`, and
`crates/core/src/capability.rs:284-294` makes `grant_permission(EnvironmentInspect)` a hard error with
no alternative. The same document says the opposite at `:181`: "environment.inspect can never be
authorized at all."

#### (e) An asserted negative-control test does not exist

`docs/SECURITY-STATUS.md:127` claims "Removing the low-integrity step makes the same test fail."
`crates/sandbox/tests/containment.rs:229-291` contains no such variant. Its assertions are that the
inside file exists (`:263`), the created file carries the low label (`:267-271`), the outside file does
not (`:272`), and — as a separate control — that the trusted parent *can* write the outside path
(`:287-290`). A repository-wide search returns no negative-control containment test.

#### (f) "Empty environment" is a default, not an invariant

The mechanism is real and correct (see [§3.4](#34-empty-environment-verified-no-gap)). But
`crates/sandbox/src/containment/spawn.rs:80-83` exposes a public
`ContainedProcessSpawner::with_inherited_environment()` whose own documentation says it "hands the child
every variable the operator exported, including provider credentials." It has no caller in this
repository, so nothing is currently wrong, but the guarantee is a default a future caller can opt out
of with one method call and no declaration, no validation, and no log line. Closed in this milestone;
see [§7](#7-follow-up-actions-taken).

#### (g) "A model may ask for the permission" — only a mock strategy can

`docs/SECURITY-STATUS.md:22` and `ARCHITECTURE.md:102` say a model may ask for the `process.spawn`
permission. The only producers of `ModelDecision::CapabilityProbe` are ten `MockModelConfig` strategies
(`ForbiddenActionSpam` at `crates/model-adapters/src/lib.rs:734`, plus the five security probes). The
real OpenAI-compatible adapter returns only `ModelDecision::GridAction`
(`crates/model-adapters/src/lib.rs:629`), its `PromptRequest` carries no capability field, and
`crates/model-adapters/src/lib.rs:1653` asserts exactly that. `crates/engine/src/lib.rs:400` is the
only place a `CapabilityProbe` is matched.

### 2.3 Undocumented shipped behaviour

The v0.4.1 commit touched 12 files, **none of them documentation**. Two mechanisms with security
relevance are absent from all four documents.

**Wall-clock timeout enforcement and force-kill.** `TerminationReason::Timeout` exists at
`crates/core/src/execution.rs:149-162` with the comment "The job object does not bound wall-clock time."
A plan is invalid until `with_timeout` is called (`:314-318`, `:399-403`) — "an undeclared timeout
would be an unbounded child" — and an undeclared or zero timeout is refused at validation
(`:281-291`). The spawner waits then terminates the job (`:107-109`, `:202-224`), recording
`Timeout` with **no** exit code (`:382-387`: "a process stopped by timeout must not report an exit code
it never chose"). Doc coverage today is one vague clause at `docs/SECURITY-STATUS.md:35`. The
exhaustive job-limit enumerations at `ARCHITECTURE.md:140`, `PROGRESS.md:20`, and
`docs/SECURITY-STATUS.md:48`/`:122` list seven kernel limits and never mention the wall-clock bound.
Nobody reading the documentation could author a valid `ProcessSpawnPlan`.

**stdout/stderr capture with byte counts.** `STREAM_PREVIEW_LIMIT` is 4096
(`crates/core/src/execution.rs:172`); `StreamCapture` carries `bytes`, `preview`, and `truncated`
(`:174-210`). Capture files are written inside the designated directory
(`crates/sandbox/src/containment/spawn.rs:126-127`, `:155-156`), byte count is read from file length
(`:263`), and the preview is bounded in both bytes and characters (`:274-290`). Validation rejects an
over-cap preview, a `truncated` flag disagreeing with the byte count, or an untruncated capture missing
content (`crates/telemetry/src/lib.rs:411-433`). **Doc coverage today: zero mentions of stdout,
stderr, capture, or byte counts in any of the four documents.**

A related sub-gap with real security weight is also undocumented: standard input is pointed at the
`NUL` device (`crates/sandbox/src/containment/windows.rs:1098`, comment `:435-436`), so a child can
never block on or read from the operator's console.

Two further undocumented operational constraints: a plan must name an **absolute** program path,
because a child with an empty environment has no `PATH` (`crates/core/src/execution.rs:297-305`); and
`crates/sandbox/src/containment/spawn.rs:307-320` strips the `\\?\` verbatim prefix from the child's
working directory because `cmd.exe` otherwise silently falls back to its own directory.

### 3.2 MIC path protection against a real child

`cargo test -p probelab-sandbox --locked --test protection` — **7 passed, 0 failed**. The decisive test

### 3.3 Timeout force-kill against a real hang

`enforced::a_child_that_outlives_its_declared_timeout_is_killed_with_the_job`
(`crates/engine/tests/process_spawn.rs:530-615`).

- Declared timeout: **1500 ms** (`:40`)
- The child is `ping -n 60 127.0.0.1`, which would run ~60 s using almost no CPU, so **no job-object
  limit can end it** — only the host's wall-clock timer can (`:533-535`)
- Measured: the test completed in **1.53 s**; the whole test binary invocation took 2.22 s
- `execution.spawned == true`, `execution.termination == TerminationReason::Timeout`
- `execution.exit_code == None` — "the host stopped this child, so the child never chose an exit code"
- `is_process_alive(pid) == false` — the process table confirms the child is gone
- `integrity.total_events() == 0` — "a timeout is not a model violation"

The whole job is terminated rather than the tracked process alone, with `KILL_ON_JOB_CLOSE` as a drop
backstop, so nothing the child started outlives it (`:603-604`).

### 3.4 Empty environment — verified, no gap

This was the highest-risk item to confirm, because a single `std::env::vars_os()` sits in the spawn
path. Traced directly:

- `crates/sandbox/src/containment/windows.rs:451-460` — `spec.inherits_environment()` is false, so the
  `else` branch always supplies an explicit block. The comment records the trap precisely: "Passing
  `None` here would mean *inherit the parent's block*."
- `environment_block(overrides, false)` at `:1248-1286` starts from `Vec::new()`, and `:1278-1284`
  emits the two-NUL empty block, with the comment that `CreateProcessW` rejects a bare single NUL with
  `ERROR_INVALID_PARAMETER`.
- The `std::env::vars_os().collect()` at `:1254` is on the `inherit == true` arm only and is therefore

  `ContainedProcessSpawner::with_inherited_environment()` (`crates/sandbox/src/containment/spawn.rs:80`),

The escape hatch itself was a finding — public, documented as handing over provider credentials, and
callable with no declaration or validation — and is closed in this milestone.

### 3.5 stdio capture byte-count accuracy

`enforced::a_child_that_writes_more_than_the_preview_cap_is_byte_counted_not_stored_whole`
(`crates/engine/tests/process_spawn.rs:617-688`) — **passing**. Measured facts:

- Ground truth for that payload is ~25.5 kB (9 lines × 62 B + 90 × 63 B + 301 × 64 B), far above the
  4096-byte preview cap
- `stream.bytes > STREAM_PREVIEW_LIMIT` — asserted
- `stream.truncated == true` — asserted
- `stream.preview.chars().count() == 4096` **exactly** — "the preview must be capped, not merely
  shortened" (`:662-666`)
- the tail marker `PROBELAB-LOUD-MARKER-400` is proven **absent** from the preview and **present** in
  the file, so the whole stream is neither stored in telemetry nor lost
- `stream.bytes` equals the capture file's length on disk

**Honest caveat.** The final assertion is self-referential: `stream.bytes` is *derived* from that
file's length (`crates/sandbox/src/containment/spawn.rs:263`) and is then compared to the same file's
length. A systematic counting error would still pass. The test proves the plumbing and the bounding,
not absolute correctness against an independent ground truth. It is a good test; it is not a proof of
byte-count accuracy in the strong sense.

## 4. Is the benchmark itself any good?

**No. This is the most important finding in the audit.**

The grid-world benchmark as currently implemented does not measure reasoning ability. It is a 25-cell,
branching-free, fully-observable path-following task with a hardcoded goal, solved optimally in 8 of 30
available turns by a three-comparison greedy rule. The repo already ships that rule as a mock strategy.
A single episode on a single hardcoded seed is reported with no aggregation and no baseline.

The engineering *around* the benchmark — trusted engine, deny-all broker, append-only telemetry, replay
digests, integrity accounting, an evaluator that refuses to trust model-reported results — is genuinely
disciplined and unusually well built. None of it is a capability measurement.

### 4.1 Visibility model

Radius-1 partial observability, five tiles per turn. The `Observation` struct
(`crates/core/src/observation.rs:46-65`) carries `turn`, `position`, `grid_size`, `current_tile`,
`visible_neighbors`, `max_turns`, `remaining_turns`, and `available_actions`. Rendering
(`crates/sandbox/src/lib.rs:159-187`) is a four-neighbour cross plus the current tile; there is no
ASCII grid.

Neither the reward nor the danger position is visible until adjacent — but this is irrelevant, because
**both are compile-time constants that do not depend on the seed**:

```rust
// crates/sandbox/src/lib.rs:24-29
const WIDTH: u8 = 5;
const HEIGHT: u8 = 5;
const START_X: u8 = 0;
const START_Y: u8 = 0;
const REWARD_X: u8 = 4;
const REWARD_Y: u8 = 4;
```

The generator writes the reward unconditionally at `(4,4)` after the corridor fill
(`:388-391`), and the start is hardcoded at `(0,0)` (`:76-79`, `:379-382`). `grid_size` is disclosed
every turn (`:89-94`). **A model can hardcode "go to the max-x/max-y corner" and never need to see the
board, the map, the seed, or the reward tile.**

There is no fog of war in the tile-kind sense — every visible tile is fully labelled
`safe`/`obstacle`/`danger`/`reward` (`crates/core/src/observation.rs:25-35`) — and no "unknown" tile
exists.

**Memory is not merely unused; it is structurally impossible.** The provider sends exactly two messages
per call, one system prompt and one user request, with no history
(`crates/model-adapters/src/lib.rs:504-513`). The model never sees its own past actions or
observations. The harness therefore cannot measure exploration, map-building, or credit assignment, in
principle. The observation is Markovian by construction, which structurally selects for reactive
greedy policies.

**The objective is never stated.** `prompts/grid_world_v1.md` is 19 lines and contains zero occurrences
of "reward", "danger", "obstacle", "goal", "win", or "score". Part of the measured capability is
inferring the objective from English token names.

### 4.2 A trivial heuristic is not merely competitive — it is optimal

The generator, quoted in full (`crates/sandbox/src/lib.rs:345-394`):

```rust
fn generate_map(seed: u64) -> [TileKind; 25] {
    let mut rng = ChaCha8Rng::seed_from_u64(seed);
    let mut corridor = [false; 25];
    let mut x = START_X;  let mut y = START_Y;
    corridor[cell_index(Coordinate { x, y })] = true;
    while x < REWARD_X || y < REWARD_Y {
        if x == REWARD_X { y += 1; }
        else if y == REWARD_Y { x += 1; }
        else if rng.random_bool(0.5) { y += 1; }
        else { x += 1; }
        corridor[cell_index(Coordinate { x, y })] = true;
    }
    let mut map = [TileKind::Obstacle; 25];
    let remaining = (0..25).filter(|i| !corridor[*i]).collect::<Vec<_>>();
    let mut danger_placed = false;
    for index in remaining {
        let danger = rng.random_bool(0.35) || !danger_placed;
        map[index] = if danger { danger_placed = true; TileKind::Danger } else { TileKind::Obstacle };
    }
    map[cell_index(Coordinate { x: START_X, y: START_Y })] = TileKind::Safe;
    for index in 0..25 { if corridor[index] { map[index] = TileKind::Safe; } }
    map[cell_index(Coordinate { x: REWARD_X, y: REWARD_Y })] = TileKind::Reward;
    map
}
```

What this actually produces:

1. The "randomised" part is **a single coin flip per step** choosing Right versus Down. The walk is
   strictly monotone, so the corridor is a staircase of **exactly `REWARD_X + REWARD_Y` = 8 steps** —
   nine safe cells — for **every seed, with zero variance**.
2. **Every one of the other 16 cells is Obstacle or Danger. There are no Safe cells outside the
   corridor.** The Safe set is exactly a nine-cell path.
3. Because the path is monotone, two non-consecutive path cells are never Manhattan-adjacent. The Safe
   region is therefore a **simple path graph with zero branches, zero loops, and zero dead ends**.
4. Danger cells are all *off* the path, so they are pure traps for deviators; a correct walker never
   meets one.

At every interior cell there is exactly one safe onward move. The "optimal policy" is a total function
of the local observation with a one-step horizon, and that is precisely the mock's `optimal_action`
(`crates/model-adapters/src/lib.rs:972-996`): three comparisons, preferring a Safe neighbour and then
a Reward. No search, no planning, no memory, no backtracking, no lookahead. It is asserted to win in
exactly 8 turns (`crates/engine/tests/vertical_slice.rs:211-212`).

### 4.3 Reward structure

| Quantity | Value |
| --- | --- |
| Grid | 5 × 5 = 25 cells |
| Start / reward | `(0,0)` / `(4,4)`, both **seed-independent** |
| Safe cells | 9, identical count every seed |
| Optimal path | 8 moves, zero variance |
| Turn limit | 30 (`crates/sandbox/src/lib.rs:36`, `benchmarks/games/grid-world.v1.json:8`) |
| Slack | 22 wasted turns, 3.75× the optimal path |
| `total_reward` possible values | **{0, +10, −10}** |
| Partial credit | **none** |

Scoring is at `crates/sandbox/src/lib.rs:218-227`: 0 for Safe, Invalid, or Waited; −10 for Danger; +10
for Reward. A move into an Obstacle is `Invalid` — it stays in place, consumes a turn, and does **not**
terminate (`:204-231`).

Because Danger and Reward are the only scoring tiles and both are terminal, `total_reward` carries
**one bit**. A model that walks 22 correct steps toward the goal and times out scores **exactly 0** —
identical to a model that emits `WAIT` thirty times. `task_success` is a pure function of the terminal
enum (`crates/evaluator/src/lib.rs:102-108`).

A random-walk baseline is not recorded anywhere; the shipped `Random` strategy is only ever asserted to
be deterministic (`vertical_slice.rs:414-426`), never to succeed or fail. Note that
`random_action` (`crates/model-adapters/src/lib.rs:998-1017`) filters only `tile != Obstacle`, so it
**will** walk into Danger. Separately, on a nine-node path with a reflecting end, a safe-only random
walk has mean hitting time 64 and P(T ≤ 30) ≈ 0.15 — so roughly **10–15 % of purely random,
non-reasoning policies succeed anyway**, because the only failure modes are stepping on a trap and
running out of budget, and the budget is forgiving.

### 4.4 Aggregation: there is none

The engine's run function contains exactly one episode loop and one evaluator call
(`crates/engine/src/lib.rs:294`, `:690`). The desktop command invokes it once per user action with the
seed hardwired to the benchmark default (`apps/desktop/src-tauri/src/commands.rs:57`, `:72-81`).

A search for `calibrat|episodes|trials|aggregate|mean|average|stdev|variance|confidence` across the
benchmark and harness paths returns **zero hits**. The only aggregation in the codebase is
`TokenUsage::add_assign` across model calls within a single episode — token counting, not statistics.

- Episodes per run: **1**
- Seeds per run: **1**, always `123` (`benchmarks/games/grid-world.v1.json:7`)
- Baselines recorded: **none**
- Threshold or pass mark: **none**
- Composite score or weights: **none exist**; `CapabilityResult` (`crates/core/src/result.rs:126-144`)
  is a seven-field tuple

The vertical-slice "matrix" (`vertical_slice.rs:172-187`) iterates nine mock strategies on seed 123.
That is a test matrix, not a sample.

**Reported honestly: a binary outcome from n = 1 on one board is an anecdote, not a capability
measurement.** The Wilson 95 % interval on a 1/1 success is approximately [0.21, 1.00]. Any
leaderboard claim built on this is noise.

### 4.5 Seed leakage

There is no calibration phase, so there is no calibration/test split to leak across. The problem is
worse in a simpler form: **the board is a constant.**

- `default_seed: 123` is a hardcoded literal (`benchmarks/games/grid-world.v1.json:7`), asserted at
  `crates/benchmarks/src/lib.rs:285`
- the seed is **not configurable** — every UI run uses `summary.seed`
  (`apps/desktop/src-tauri/src/commands.rs:57`), there is no seed input in the frontend, and the value
  is *displayed* read-only (`apps/desktop/src/App.tsx:880`, `:998`, `:1254`)
- `same_seed_and_strategy_produce_field_identical_results_across_files_and_run_ids`
  (`vertical_slice.rs:391-399`) and `every_v0_1_strategy_replays_to_its_recorded_v0_2_digest`
  (`:132-187`) pin this behaviour
- the seed barely matters: start and goal are constants, so a fixed 8-move `MOVE_*` script derived from
  the seed-123 corridor works, and a "walk to the max-x/max-y corner" script works on **every** seed

The repository already demonstrates the exploit. Both `ScriptedAgent`s
(`crates/engine/tests/protocol.rs:35-84`, `crates/engine/tests/capability_broker.rs:68-96`) replay a
fixed decision list and then fall back to `WAIT` — a zero-generalization, zero-reasoning hardcoded
policy that produces a full, legitimate `TestResult` with `task_success: true`. The harness cannot
distinguish it from a reasoning model.

The one clean thing: `episode_id` does not leak the seed (`crates/sandbox/src/lib.rs:73`, asserted at
`:660-663`), and `prompts/grid_world_v1.md` contains no example board, so there is no few-shot leakage.

### 4.6 `protocol_adherence` versus `game_performance`

They are not two measurements. They are one measurement with a pre-filter, because **the world only
moves on a protocol-valid turn.** On any protocol failure the engine burns a turn via
`consume_protocol_failure_turn` (`crates/engine/src/lib.rs:336-352`), incrementing `turns_used` and
leaving the grid untouched (`crates/sandbox/src/lib.rs:116-134`). An out-of-vocabulary action is
converted to a protocol failure *before* the sandbox sees it (`crates/engine/src/lib.rs:323-326`,
`:739-755`).

| Direction | Relationship |
| --- | --- |
| `task_success ⟹ protocol_adherence == 100 %` | **Guaranteed.** Winning needs eight consecutive in-vocabulary, well-formed responses; one failure makes success impossible. |
| `protocol_adherence == 100 % ⟹ task_success` | **False.** `WAIT` × 30 gives 100 % protocol adherence, `total_reward: 0`, `TurnLimit`. See `crates/engine/tests/protocol.rs:152-204`: two parse failures then 28 valid `WAIT`s. |

So `protocol_adherence` is a **necessary gate**, and `game_performance` is the outcome conditioned on
passing the gate. A successful run is *by construction* the maximally protocol-adherent run.

**What `game_performance` adds on top: exactly one bit** — did the model avoid stepping on the
labelled `danger` tile while monotonically approaching a hardcoded corner. Given
[§4.2](#42-a-trivial-heuristic-is-not-merely-competitive--it-is-optimal), that bit is decided by three
local comparisons. There is no route selection, no resource trade-off, no irreversibility, no
adversarial element, no horizon beyond one tile.

`PROTOCOL_FAILURE_THRESHOLD = 3` (`crates/core/src/result.rs:45`) is a hardcoded constant that
materially affects real-model scoring: three unparseable responses in a row ends the run with a hard
zero regardless of how well the model "planned." That makes the headline metric substantially a
JSON-formatting-compliance measure.

### 4.7 Verdict

The benchmark currently measures, at most, two things:

1. can the model emit one well-formed JSON object containing one of five literal strings, and
2. can it apply a three-rule greedy monotone walk toward a coordinate that is a compile-time constant.

The honest label is **an integration test of the harness, with a deterministic mock as the model**.
Calling the output "grid-world planning" overstates it by roughly the entire gap between
`if neighbour is safe, step toward (4,4)` and planning.

The minimum honest changes are recorded as the next milestone: seed the goal and hazards per seed;
introduce genuine partial observability so information must be gathered and held; make the safe region
branch with route-length trade-offs and irreversible hazards; run N ≥ 30 episodes over a held-out seed
set disjoint from any dev set; record random and greedy baselines per seed; and report a scalar with a
confidence interval.

## 6. UI audit

The desktop IPC surface is six commands and three events
(`apps/desktop/src-tauri/src/lib.rs:148-155`), and every result-returning command returns a whole
struct. The consequence is important: **almost nothing is withheld by the command layer.** The data
crosses IPC in full and is dropped in React. This is a rendering gap, not an architecture gap.

There is a second structural fact colouring everything below: the only catalogued benchmark grants
nothing and declares no spawn plan, so `process_lifecycle` events, authorized spawns, and
`CapabilityExecutionUnsupported` are **structurally unreachable from the desktop today**. Those gaps are
contract gaps rather than live ones. Everything else below is reproducible with the shipped mocks.

| stdout/stderr `bytes` | yes | **no** |
| stdout/stderr `preview`, `truncated` | yes | **no** |
| `ProcessExecution.pid`, `exit_code` | yes | **no** |

### 6.2 Correctness and honesty problems

1. **`PROMPT /` in the provider card shows the last run's value**, not the current configuration. The
   correct value is computed into `connectedPromptVersion` (`App.tsx:610`) and never used.
2. **Two contradictory model identities on screen at once.** `get_provider_status` is only ever called
   with the connected config (`:658`), so during a mock run the provider card asserts
   `openai-compatible` while the result panel shows `deterministic-mock` / `native-mock-optimal`.
3. **`CREDENTIAL / environment` is a hardcoded fallback** (`:925`) that is wrong for the mock provider,
   whose real value is `none` (`apps/desktop/src-tauri/src/provider.rs:326`).
4. **`INTEGRITY EVENTS` merges two layers the architecture insists are disjoint**, and sits directly
   above a separately-titled `BROKER REFUSALS` panel — inviting precisely the conflation
   `crates/core/src/result.rs:146-152` and `docs/SECURITY-STATUS.md:100` exist to prevent. With no
   compliance verdict, the number carries no pass/fail meaning.
5. **An aborted run shows zero metrics.** `runState: "error"` renders the banner, and the entire metric
   block is gated on `result` (`:1206`), which is null. Partial integrity, protocol, and token data
   already delivered over telemetry is never summarised.
6. **A run failure does not change `SYSTEM ONLINE`.** `systemStatus` (`:563-571`) considers only
   benchmark and listener errors.
7. **`runId` is not cleared on a new run** (`:784-787`), so the previous run's ID is shown while the new
   run is starting.
8. **Benchmark selection is fake.** `benchmarks[0]` is always the target (`:551`); only one row is
   rendered; the index is hardcoded `01`; `SELECTED` is unconditional — yet the badge reports
   `benchmarks.length`.
9. **`INVALID ACTIONS` is overloaded.** The protocol counter (model emitted an out-of-vocabulary action,
   a model-quality signal) is hidden, while the environment counter (a boundary or obstacle was bumped,
   a world signal) is rendered under that label.
10. **The action-trace table has four unlabelled columns** and no `<table>` semantics; the telemetry
    list truncates at 10 rows with no count, scroll, or expand affordance; the broker panel has no empty
    state and is silently absent when zero; `LIMIT` conflates the episode turn limit with a timeout; the
    same enum value is rendered in two different casings on one screen; and the provider pill asserts
    `NOT CONFIGURED` during its 180 ms debounce, before any answer has arrived.
11. **`GRID-WORLD PLANNING` is hardcoded** (`App.tsx:855`) while `capability_dimension` is received and
    unused — it would silently disagree the moment a second benchmark is registered.

### 6.3 Mock versus connected

The security panels are **not** mode-gated; they render from `result.integrity` regardless of which
button was pressed. The important asymmetry: the five `security_probe_*` strategies and
`forbidden_action_spam` **can** populate the broker panel, while in connected mode those panels are
**structurally always zero**, because a real provider cannot emit a `CapabilityProbe`. Nothing in the
UI states that connected runs cannot generate integrity events. The operator cannot distinguish "the run
was clean" from "this path cannot produce a denial."

The mock strategy `<select>` also sits *inside* the connected-provider card, above a mock-only footer,
with descriptive prose that reads as though it might govern a connected run. It cannot.

## 7. Follow-up actions taken

This section records what was changed in direct response to the findings above, so that a later reader
can separate the audit from its remediation.

- **A2 — documentation corrections.** The false "authorized or denied" lifecycle claim, the
  "library nothing calls" implication, the fingerprint field count, the `environment.inspect`
  contradiction, the non-existent negative-control test claim, the 212 test count, and the one broken
  reference were all corrected to match the code. Version and commit stamps were added to the four
  narrative documents. The v0.4.1 timeout and stream-capture contracts were documented.
- **A3 — the AppContainer postmortem was recovered and preserved.** It existed **only** as a module
  comment in an unmerged file on the wip branch
  (`crates/sandbox/src/containment/appcontainer.rs`), not in any document. Before the branch was
  deleted, two findings were recorded in `docs/SECURITY-STATUS.md`: the restricted-token approach that
  was built, proven unusable without elevation, and removed; and the `CreateAppContainerProfile`
  `HRESULT 0x80070017` failure with the pivot to `DeriveAppContainerSidFromAppContainerName`. The
  branch was then deleted locally and remotely.
- **A4 — the inherited-environment escape hatch was closed.**
  `ContainedProcessSpawner::with_inherited_environment()` was removed, so an empty child environment is
  now an invariant of the spawner rather than a default a future caller can opt out of.
